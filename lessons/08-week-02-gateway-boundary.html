Production LLM Inference Lab / Lesson 2

The inference gateway: one public API, many private details

Your next learning target is the gateway. It is the boundary that lets clients use one stable API even if the model server, model, or serving framework changes later.

The problem it solves

Right now a client can call the Week 1 model server directly at :8001/generate. That makes the client depend on private details: max_new_tokens, the internal message shape, the Qwen model, and its response fields. Replacing Hugging Face with vLLM would force every client to change.

Client→ Gateway :8000
stable public contract→ Week 1 server :8001
private backend contract→ Qwen

After Week 2, the client never knows that port 8001 exists.

The gateway’s five jobs

  1. Validate: reject malformed requests and unsafe token limits before they consume model capacity.
  2. Translate: convert the public chat request into the internal backend request, then map the backend result back to the public shape.
  3. Protect: apply a deadline and turn backend failures into predictable client errors.
  4. Observe: create a request ID and record metrics such as duration, tokens, errors, and in-flight requests.
  5. Stream: relay ordered output chunks without buffering the entire answer.

Worked example A: a successful non-streaming chat

A client calls only the gateway:

POST http://127.0.0.1:8000/v1/chat/completions
{
  "model": "local-qwen",
  "messages": [{"role": "user", "content": "Explain caching in one sentence."}],
  "max_tokens": 16,
  "stream": false
}

Trace it step by step:

  1. Assign an ID. Gateway generates req_8f31. Every log line and failure for this request gets this ID.
  2. Validate locally. Ensure messages is non-empty and max_tokens=16 is at or below the gateway policy. If it is invalid, do not call port 8001.
  3. Translate to the private contract. The Week 1 server expects a different field name and has no public model selector: 
    POST http://127.0.0.1:8001/generate
{
  "messages": [{"role": "user", "content": "Explain caching in one sentence."}],
  "max_new_tokens": 16
}
  4. Set a deadline. For example, the gateway may give the backend 30 seconds. The client does not wait forever if the backend stalls.
  5. Receive the Week 1 response. It contains private implementation information such as device: "mps" and output_tokens.
  6. Return a stable public response. The gateway maps the text into a chat-completion choice and returns the request ID. A simplified result looks like: 
    {
  "id": "req_8f31",
  "object": "chat.completion",
  "model": "local-qwen",
  "choices": [{
    "index": 0,
    "message": {"role": "assistant", "content": "Caching stores frequently used data…"},
    "finish_reason": "stop"
  }],
  "usage": {"prompt_tokens": 36, "completion_tokens": 16}
}
  7. Emit evidence. Increment successful-request and token counters; observe duration. The request ID lets you connect this metric and its logs to one user-visible response.

Worked example B: backend timeout

Same client request, but the model server stops responding.

  1. Validation has passed, so the gateway begins the backend request and starts its 30-second timer.
  2. At 30 seconds, the HTTP client raises a timeout. The gateway does not return a Python traceback and does not keep the client waiting.
  3. It increments backend_errors_total{kind="timeout"}, records the final duration, and returns a bounded gateway error. For example: 
    HTTP/1.1 504 Gateway Timeout
{
  "error": {
    "message": "The model backend did not respond before the deadline.",
    "type": "backend_timeout",
    "request_id": "req_8f31"
  }
}
  4. Now the client can safely retry or show a useful message. An operator can search req_8f31 to find the corresponding backend attempt.

The exact error schema is our project decision. The essential principle is stable, explicit behavior. FastAPI supports raising HTTP exceptions to terminate an invalid or failed request with a defined status and JSON-able detail.

Worked example C: streaming through the gateway

When stream: true, the gateway sends an internal request to /generate/stream. It must relay chunks as they arrive:

backend SSE:  data: {"index": 0, "text": "C"}
gateway SSE:  data: {"id":"req_8f31","choices":[{"delta":{"content":"C"}}]}

backend SSE:  data: {"index": 1, "text": "aching"}
gateway SSE:  data: {"id":"req_8f31","choices":[{"delta":{"content":"aching"}}]}

backend SSE:  data: [DONE]
gateway SSE:  data: [DONE]

The gateway changes the shape, but it must preserve order and completion. It should also stop its backend work if the client disconnects; otherwise invisible work continues to occupy the model.

Why test with a fake backend first?

Gateway tests should not depend on model download time, MPS performance, or generated wording. A fake backend can deliberately return a success, a delayed response, a 500 error, or known SSE chunks. That lets you prove the gateway’s contract deterministically. Then one real integration test proves that its translator works with the Week 1 server.

Build order for this lab

  1. Write the public request and response models.
  2. Write contract tests against a fake backend: success, streaming, invalid request, token-limit rejection, timeout, and backend 500.
  3. Implement the smallest non-streaming translator until its tests pass.
  4. Add streaming relay and cancellation behavior.
  5. Add request IDs and minimal metrics.
  6. Start the Week 1 server, then run one real non-streaming and one real streaming gateway test.

Retrieval practice

1. If the gateway changes max_tokens into max_new_tokens, which layer owns that translation?

The gateway. The client should only know the public contract; the model server should only receive its internal contract.

2. Why is a timeout an API behavior, not merely an implementation detail?

Without a deadline, clients cannot know when to recover and capacity can be held indefinitely. A defined timeout gives predictable failure behavior and measurable operational evidence.

3. In a streamed response, what must be preserved when mapping backend events?

Ordering, the text content, completion signaling, and cancellation handling. The public event structure may differ from the backend’s.
