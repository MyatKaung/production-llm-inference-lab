Prefill and decode: the two phases inside every answer

Short answer to your question: prefill and decode are not “after Week 1.” They occur every time an autoregressive LLM generates text. Week 1 is where we first make them visible with one local model, fixed prompts, and latency measurements. Later weeks optimize the same two phases at larger scale.

Practical task before reading on

Open week-01-baseline-server/practical-baseline.ipynb and run these four code cells in order: environment/device, tokenizer/model load, chat-template inspection, and the cell that defines make_inputs() plus generate_once(). Then run this existing smoke test:

smoke = generate_once('Explain caching in one sentence.')
print(smoke['prompt_tokens'], smoke['output_tokens'], smoke['text'])

Do not change the model, device, or sampling settings yet. Your job is to observe one prompt becoming input tokens and one completion becoming output tokens.

Start with the exact Week 1 request

POST /generate
{
  "messages": [{"role": "user", "content": "Explain caching in one sentence."}],
  "max_new_tokens": 16
}

After the Qwen chat template is added, the request is not one sentence anymore from the model’s perspective. It becomes a sequence of token IDs—including role markers and generation markers. Our actual short-prompt run contained 36 input tokens.

Phase 1: prefill

36 prompt tokens→ one forward pass over the prompt→ KV cache for those positions→ logits for the first answer token

Prefill means “read the whole prompt and prepare context.” The transformer processes the input positions and produces key/value (KV) states for every layer and token position. Those states are saved in the KV cache.

Think of reading a question before replying. You need to take in all of it before you can write the first word. A longer prompt means more initial reading work, which usually increases time to first token (TTFT).

Why the KV cache exists

At the first output step, the model can attend to the prompt. At the second output step, it needs the prompt and the first output token. Recomputing the whole prompt on every output token would waste work.

Without cache, to produce each next token:
  recompute prompt + all earlier generated tokens

With cache, to produce each next token:
  reuse earlier keys/values + compute only the new token's keys/values

The cache trades memory for speed. It grows as the context and answer grow, which is why long-context serving eventually becomes a memory-management problem as well as a latency problem.

Phase 2: decode

first generated token→ append its KV state→ predict next token→ repeat until stop / limit

Decode is the repeated loop that produces one new token at a time. With do_sample=False, our Week 1 notebook uses greedy decoding: at each step it chooses the highest-scoring next token.

For the streamed response, the server emitted token fragments such as:

step 1 → "C"
step 2 → "aching"
step 3 → " is"
step 4 → " the"
...
final → [DONE]

These are tokenizer units, not guaranteed whole words. Streaming lets the user see them during decode rather than waiting for the full sequence.

Worked example: walk through four decode steps

  1. Prefill: Qwen reads the 36 prompt tokens and fills its KV cache. It produces a score for every possible first output token.
  2. Decode step 1: greedy selection picks token ID 34, decoded as "C". The model adds that token’s KV values to the cache.
  3. Decode step 2: using cached prompt context plus "C", it picks token ID 11829, decoded as "aching". Now the visible text is "Caching".
  4. Decode step 3: using the expanded cache, it picks " is". This repeats until an end token or the configured output limit is reached.

The server code expresses this with model.generate(..., use_cache=True). The non-streaming path receives all generated IDs at the end. The streaming path receives generated IDs incrementally through its streamer.

Use the measurements correctly

Our Week 1 benchmark fixed the maximum output at 64 tokens for medium and long prompts:

PromptInput tokensOutput tokensMedian total latency
Short36330.549 s
Medium45641.066 s
Long1,111641.358 s

Medium and long have the same output cap, but long has 1,066 more input tokens and a higher median total latency. That is consistent with more prefill work. But this is not a clean pure-prefill measurement: total latency also contains decode. To separate them more convincingly, we need streaming TTFT and inter-token timing—which the second Week 1 notebook begins to collect.

Which knob affects which phase?

  • More prompt tokens: primarily increases prefill work and TTFT.
  • More output tokens: primarily adds more decode iterations and total latency.
  • More concurrent requests: can add queueing and scheduling interference to both.
  • KV-cache capacity: affects how many/long requests fit in memory, and later drives paging, eviction, prefix caching, and batching choices.

Where this appears in the roadmap

  1. Week 1: observe prefill/decode with a single local model; measure tokens, streaming, and latency.
  2. Week 2: preserve this behavior through a gateway; do not let API translation hide latency or streaming errors.
  3. Weeks 3–6: measure bottlenecks and optimize batching, cache use, quantization, and vLLM scheduling.
  4. Weeks 7–10: use the same concepts for SGLang, distributed strategies, and production capacity decisions.

Retrieval practice

1. Which phase must finish before the first streamed token can appear?

Prefill must process the prompt and create the context needed to predict the first token. TTFT includes this work plus the first decode step and surrounding overhead.

2. Why doesn’t the model recompute the full prompt for every generated token?

The KV cache stores prior attention keys and values. Decode reuses them and computes only the newly appended token state.

3. If output length stays fixed but input length grows from 45 to 1,111 tokens, which phase is the main new cost?

Prefill. Decode still runs for the same capped output length, while the model must process a much longer prompt before beginning it.
