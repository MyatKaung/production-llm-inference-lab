Designing the gateway’s public contract and private backend interface

This is the bridge from understanding the gateway to implementing it. We will name the data that crosses each boundary before writing the route.

One request, three representations

Public client JSON
max_tokens→ Gateway internal objects
validated + policy checked→ Week 1 backend JSON
max_new_tokens

They may look similar, but they have different owners. The client owns the public request; the Week 1 server owns its private request. The gateway owns the translation between them.

Contract 1: the public client request

For this lab, the gateway accepts a deliberately small OpenAI-compatible subset:

POST /v1/chat/completions
{
  "model": "local-qwen",
  "messages": [
    {"role": "system", "content": "Answer concisely."},
    {"role": "user", "content": "Explain caching in one sentence."}
  ],
  "max_tokens": 16,
  "stream": false
}

Its Pydantic model can say exactly what we promise to accept:

class ChatMessage(BaseModel):
    role: Literal["system", "user", "assistant"]
    content: str = Field(min_length=1)

class ChatCompletionRequest(BaseModel):
    model: str = Field(min_length=1)
    messages: list[ChatMessage] = Field(min_length=1)
    max_tokens: int = Field(default=64, ge=1)
    stream: bool = False

Important: the type model checks structural validity: the fields exist and have valid types. The gateway policy checks operational validity: for example, max_tokens <= 128 and the message count or input-token estimate is within the configured limit.

Worked example A: structural validation versus policy validation

These two failures sound similar but occur at different layers:

Malformed JSON / structural failure

{"model": "local-qwen", "messages": []}

This violates Field(min_length=1). FastAPI/Pydantic responds with 422 before our route executes.

Well-formed but disallowed / policy failure

{"model":"local-qwen", "messages":[{"role":"user","content":"Hi"}], "max_tokens":500}

This parses successfully, but our gateway’s limit is 128. The route returns a designed 400-style error and does not call the backend.

The distinction helps users and tests: “you sent invalid JSON” is different from “your valid request violates this service’s resource policy.”

Contract 2: the private backend request

The current Week 1 server accepts this exact shape:

POST http://127.0.0.1:8001/generate
{
  "messages": [
    {"role": "system", "content": "Answer concisely."},
    {"role": "user", "content": "Explain caching in one sentence."}
  ],
  "max_new_tokens": 16
}

Notice the differences: it does not accept the public model field, calls the token limit max_new_tokens, and does not know whether the original client asked for streaming.

class BackendGenerateRequest(BaseModel):
    messages: list[ChatMessage]
    max_new_tokens: int

Worked example B: explicit translation

The translation should be a small function with no network work inside it:

def to_backend_request(public: ChatCompletionRequest) -> BackendGenerateRequest:
    return BackendGenerateRequest(
        messages=public.messages,
        max_new_tokens=public.max_tokens,
    )

Given the public request above, the gateway removes model: "local-qwen" after using it to select/validate the configured backend, then renames max_tokens to max_new_tokens. This tiny function is valuable because it can be tested without HTTP or a model.

Contract 3: the backend result

The Week 1 /generate endpoint returns implementation-oriented fields:

{
  "text": "Caching stores frequently used data…",
  "prompt_tokens": 36,
  "output_tokens": 16,
  "total_latency_seconds": 1.69,
  "output_tokens_per_second": 9.49,
  "model_id": "Qwen/Qwen2.5-0.5B-Instruct",
  "device": "mps"
}

The gateway needs only a stable subset to construct the public result:

@dataclass
class BackendResult:
    text: str
    prompt_tokens: int
    output_tokens: int
    backend_model_id: str

Latency and device fields are still useful—but for internal logs and metrics, not necessarily the public API. This avoids accidentally making MPS or Hugging Face part of the client contract.

Worked example C: map the result to a public response

def to_public_response(result: BackendResult, *, request_id: str, model: str):
    return {
        "id": request_id,
        "object": "chat.completion",
        "model": model,
        "choices": [{
            "index": 0,
            "message": {"role": "assistant", "content": result.text},
            "finish_reason": "stop",
        }],
        "usage": {
            "prompt_tokens": result.prompt_tokens,
            "completion_tokens": result.output_tokens,
            "total_tokens": result.prompt_tokens + result.output_tokens,
        },
    }

If the backend returned 36 prompt tokens and 16 output tokens, the public response reports 52 total tokens. That arithmetic belongs to the mapping layer, so a fake backend can test it exactly.

The backend interface: the seam that enables both fakes and future engines

class InferenceBackend(Protocol):
    async def generate(self, request: BackendGenerateRequest) -> BackendResult: ...
    async def stream(self, request: BackendGenerateRequest) -> AsyncIterator[BackendChunk]: ...

There will be two implementations:

  • FakeBackend: returns fixed BackendResult objects in contract tests.
  • HttpWeek1Backend: serializes BackendGenerateRequest, calls port 8001, parses the response, and turns HTTP/network failures into typed backend errors.

Later, a VllmBackend can implement the same interface. The route and client contract stay unchanged.

Worked example D: the route stays thin

@app.post("/v1/chat/completions")
async def chat_completions(
    request: ChatCompletionRequest,
    backend: InferenceBackend = Depends(get_backend),
):
    enforce_limits(request)                  # no backend call if rejected
    request_id = new_request_id()
    internal = to_backend_request(request)   # pure translation
    result = await backend.generate(internal)
    return to_public_response(result, request_id=request_id, model=request.model)

The route reads like a short policy: validate, enforce limits, translate, delegate, map. That makes it easier to test and prevents model-server details from leaking everywhere.

What to test before implementation is “done”

  1. Empty messages produces 422 without entering the route.
  2. max_tokens=500 produces the policy error and fake backend calls remain empty.
  3. A known fake result maps to correct choices and usage.total_tokens.
  4. A fake timeout maps to the gateway’s bounded timeout error with a request ID.
  5. The HTTP backend successfully translates one real request to port 8001.

Retrieval practice

1. Where should max_tokens become max_new_tokens, and why?

In the gateway translation function. The name difference is a private backend detail; clients should not need to know it.

2. Which backend fields should appear in the public response: device, total_latency_seconds, or token usage?

Token usage is part of the useful client response. Device and implementation latency belong in internal telemetry unless the public contract explicitly promises them.

3. What needs to change to switch from the Week 1 HTTP server to vLLM later?

Implement a new backend adapter that obeys InferenceBackend; keep the public models, route, and clients stable.
