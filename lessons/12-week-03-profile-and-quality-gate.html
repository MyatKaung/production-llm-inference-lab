Course map / Week 3.1

Profile the system and protect answer quality

Weeks 1 and 2 proved that one model can serve requests and that a gateway can hide the model-server details. Week 3 answers a different question: What does the system do under controlled workloads, and can later optimizations make it faster without making answers worse?

The Week 3 outcome

fixed evaluation set→ deterministic scorer→ gateway benchmark matrix→ controlled pressure case→ bottleneck report

The result is a baseline that every later change—quantization, batching, vLLM, or tuning—must compare against.

Part 1: create the quality gate first

Performance data is not enough. A faster configuration that produces worse answers is not automatically an improvement. Before measuring any optimization, make a fixed set of 10–20 prompts and score the results using deterministic rules.

Worked example: property-based scoring

This test does not require one exact sentence. It requires observable properties.

{
  "id": "extract-01",
  "category": "extraction",
  "messages": [
    {"role": "user", "content": "Extract the city from: Alice moved to Singapore in 2024."}
  ],
  "expected": {
    "contains": ["Singapore"],
    "not_contains": ["Kuala Lumpur"]
  }
}

A deterministic scorer can lower-case the completion, verify that it contains singapore, and verify that it does not contain kuala lumpur. The result is pass or fail—no language-model judge and no subjective hand scoring.

Suggested categories:

  • instruction following;
  • fact extraction;
  • short summarization;
  • simple structured JSON;
  • basic reasoning with a known answer;
  • refusal or safety behavior relevant to your application.

Practical check

  1. Run the same evaluation set through POST :8000/v1/chat/completions twice.
  2. Use do_sample=false in the Week 1 backend, so the answers are deterministic.
  3. Confirm that both runs have the same score.
  4. Save that score as the baseline quality gate.

Do not change the prompts, model revision, sampling configuration, or scorer between before/after experiments. If you change the ruler, you cannot compare the measurements.

Part 2: benchmark the public system, not only Qwen

Your primary Week 3 benchmark goes through the gateway. The user-visible system includes both the gateway and the model server.

benchmark client→ gateway :8000→ Week 1 server :8001→ Qwen

The client must not call port 8001 directly for the main report. A direct request can be useful later as a diagnostic comparison, but it is not the public system’s end-to-end result.

The fixed matrix

Prompt lengthConcurrencyPurpose
128 tokens1, 4, 16Interactive, short-context behavior
1K tokens1, 4, 16Moderate prefill pressure
4K tokens1, 4, 16Long-context prefill pressure

This creates nine benchmark cells. Start with 2 warm-up waves and 10 measured waves per cell. A wave contains the configured concurrency, so one concurrency-16 wave means 16 requests begin together. The client runs every concurrency-1 cell first, then stops after the first failed concurrent wave by default; this preserves valid evidence instead of repeatedly sending work to an unhealthy backend. Use a fixed 64-token output limit and greedy generation.

Worked example: one benchmark row

{
  "prompt_length_target": 1024,
  "actual_prompt_tokens": 1017,
  "concurrency": 4,
  "max_tokens": 64,
  "warmups": 2,
  "measured_request": 3,
  "ttft_seconds": 0.42,
  "total_latency_seconds": 1.51,
  "output_tokens": 64,
  "status_code": 200,
  "request_id": "req_..."
}

Save raw rows like this in baseline-matrix.jsonl. Do not save only an average. Raw rows let you calculate p50 and p95 later and investigate slow outliers.

Part 3: add one controlled pressure case

The nine benchmark cells measure normal scaling. Add one deliberately demanding case so you can observe how the complete public system behaves when several long requests arrive together.

Pressure case: 4K-token prompt, concurrency 16, fixed 64-token output, after the normal warm-up.

Record the outcome rather than predicting it:

  • how many requests succeeded and how many failed;
  • p50 and p95 TTFT and total latency;
  • the gateway's in-flight request metric and backend-error metric; and
  • any visible memory-pressure or out-of-memory observation.

This is not an attempt to crash the computer. Stop if the machine becomes unresponsive or errors repeat. The lesson is to identify the first real limit of the current gateway-and-server system.

This is the useful Class 2 addition. We are not copying its engine swap or cloud setup yet. We are only adding its principle: measure the system under controlled concurrent pressure and record the failure boundary honestly.

Part 4: learn what each time means

client sends request→ waiting / queue time→ prefill→ first token: TTFT→ decode / ITL→ [DONE]
  • Queue time: waiting before the model begins work. Your current stack has no explicit admission queue, so mark it unavailable until you add queue instrumentation.
  • Prefill: processing all existing prompt tokens through the Transformer. Longer prompts usually increase this cost.
  • TTFT: client request start until the first streamed output reaches the client. It includes gateway/server overhead, prefill, and first-token delivery.
  • Inter-token latency (ITL): time between streamed token events. It describes the decode phase.
  • Total latency: client request start until the final [DONE] event.

Do not claim that client-observed TTFT is identical to pure model prefill time. It contains several pieces. Keep the measurement name honest.

Part 5: hardware feasibility before larger models

Write down whether a candidate model fits before trying to load it. Approximate FP16 weight memory as:

weight memory ≈ parameter count × 2 bytes

Then reserve extra memory for the KV cache, activations, runtime allocations, and fragmentation.

ModelFP16 weights onlyExtra memory neededDecision
3Babout 6 GBKV cache + runtimereasonable candidate
7Babout 14 GBKV cache + runtimeborderline on 18 GB unified memory
14Babout 28 GBKV cache + runtimeuse a suitable NVIDIA GPU

These are planning estimates, not guarantees. Quantization changes the calculation, but do not use quantization until the Week 3 baseline and quality score exist.

Part 6: write a bottleneck hypothesis

After the nine benchmark cells, classify each workload using evidence—not intuition.

Short prompt, concurrency 1:
  likely decode-dominated if TTFT is low and output length drives total latency.

Long prompt, concurrency 1:
  likely prefill-dominated if TTFT rises strongly with prompt length.

High concurrency:
  likely queue/scheduling-limited if tail latency rises faster than throughput.

Your report must say what you measured, what you infer, and what you could not measure yet.

Self-check

1. Why do we score quality before running Week 4 optimization experiments?

So every later performance gain can be checked against the same fixed quality baseline. Otherwise a faster but worse model configuration might look like a win.

2. Why does a 4K-token prompt usually affect TTFT more than a 128-token prompt?

The model must prefill all existing prompt tokens before it can produce the first output token.

3. Why is it wrong to report client-observed TTFT as “pure prefill time”?

TTFT also includes client, gateway, server, and first-token-delivery overhead. It is a useful user-visible metric, but it is not an isolated internal model timer.

4. What should you write if your current service has no explicit request queue?

Mark queue time unavailable. Do not guess it. Add instrumentation later if queue analysis becomes necessary.

5. What is the purpose of the deliberate pressure case?

To find and document the first limit of the current public system: rising tail latency, repeated errors, or memory pressure. It is evidence for the next engineering change, not a test you must force until the machine crashes.
