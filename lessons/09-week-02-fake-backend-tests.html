Why a fake backend makes the gateway testable

Your gateway has two responsibilities at once: accept a public client request, then call an internal model server. A fake backend replaces only the second part during most tests. It lets us control exactly what the model server does.

Real backend versus fake backend

Real backend: the Week 1 server at :8001, which loads Qwen, depends on MPS, and generates wording at variable speed.

Fake backend: a tiny in-memory object used only by tests. It can return a fixed answer immediately, throw a timeout on demand, yield known chunks, or return a 500 error.

The gateway is the thing under test. We want a failed test to mean “the gateway translated, validated, or handled an error incorrectly”—not “the laptop was busy” or “the model took longer today.”

Why this matters

  • Fast: hundreds of gateway contract tests can run in seconds, without model load or GPU work.
  • Deterministic: a fake always returns the same token count and text, so expected assertions are unambiguous.
  • Complete failure coverage: timeouts, 500s, malformed replies, and cancellation are difficult and expensive to force in a real model server, but trivial to simulate.
  • Safe design pressure: to replace the backend, the gateway must depend on a small backend interface rather than hard-coding HTTP calls everywhere.

The small interface we want

Think of the gateway as depending on this behavior, not directly on Qwen:

class Backend:
    async def generate(self, request) -> BackendResult: ...
    async def stream(self, request) -> AsyncIterator[BackendChunk]: ...

The production implementation later translates this to HTTP calls to :8001. The fake implementation returns controlled values in memory. Both obey the same interface, so the gateway does not care which one it received.

Worked example A: prove response translation

Suppose the fake backend is configured to return:

BackendResult(
    text="Caching stores reused data.",
    prompt_tokens=11,
    output_tokens=5,
    model_id="fake-qwen"
)

The test calls the gateway, not the fake directly:

response = client.post("/v1/chat/completions", json={
    "model": "local-qwen",
    "messages": [{"role": "user", "content": "What is caching?"}],
    "max_tokens": 16
})

assert response.status_code == 200
assert response.json()["choices"][0]["message"]["content"] == "Caching stores reused data."
assert response.json()["usage"] == {
    "prompt_tokens": 11,
    "completion_tokens": 5,
}

What this proves: the gateway correctly mapped its public request to the backend call, then wrapped the known backend result into the public chat-completion response. It does not prove Qwen quality or MPS speed. Those are separate integration concerns.

Worked example B: prove a bad client request never reaches the backend

Set the gateway policy to allow at most 128 output tokens. The client asks for 500:

response = client.post("/v1/chat/completions", json={
    "model": "local-qwen",
    "messages": [{"role": "user", "content": "Hello"}],
    "max_tokens": 500
})

assert response.status_code == 400
assert fake_backend.calls == []

Why a fake helps: it can keep a calls list. The assertion proves a crucial capacity rule: invalid work was rejected before it reached the model. With a real backend, you might see a 400 but still not know whether the model server was contacted.

Worked example C: force a timeout without waiting 30 seconds

A real timeout test is slow and may be flaky. Instead configure the fake to raise the same timeout exception immediately:

class TimeoutBackend:
    async def generate(self, request):
        raise BackendTimeout("simulated timeout")

response = client.post("/v1/chat/completions", json=valid_request)

assert response.status_code == 504
assert response.json()["error"]["type"] == "backend_timeout"
assert "request_id" in response.json()["error"]

What this proves: a dependency failure becomes a stable client response, includes correlation information, and increments the timeout metric. It does not mean the actual network timeout is configured correctly; that becomes one targeted integration test later.

Worked example D: prove ordered streaming translation

The fake stream yields fixed chunks:

async def stream(self, request):
    yield BackendChunk(text="C")
    yield BackendChunk(text="aching")
    yield BackendDone()

The gateway test consumes its SSE response and asserts:

assert events == [
    {"delta": {"content": "C"}},
    {"delta": {"content": "aching"}},
    "[DONE]",
]

What this proves: the gateway did not reorder, buffer, or lose chunks, and it sent a terminal completion marker. We choose split-word chunks deliberately because real tokenizers do not always produce whole words.

The two-layer testing strategy

  1. Contract tests with a fake backend: many fast tests for validation, response shape, errors, metrics, and streaming. These explain whether the gateway itself is correct.
  2. Integration tests with the real Week 1 server: a few slower tests for actual HTTP translation, model loading, and real SSE delivery. These explain whether the two components work together.

Neither layer replaces the other. Fakes give precise diagnosis; the real server gives confidence that the wiring exists.

How FastAPI and pytest support this

FastAPI supports replacing dependencies during tests, so a route can receive the fake instead of the production backend. pytest’s monkeypatch can also safely replace a network-facing object for one test, automatically undoing it afterward. Prefer an explicit backend dependency when you control the code; it makes the seam obvious.

Retrieval practice

1. If every fake-backend test passes, what has not yet been proven?

That the gateway can actually communicate with the Week 1 HTTP server and Qwen. That requires the smaller real integration suite.

2. Why assert fake_backend.calls == [] for an over-limit request?

It proves the gateway rejected invalid work before it consumed backend/model capacity, not merely that it eventually returned an error.

3. Why simulate a timeout immediately instead of sleeping for the production deadline?

The test remains fast and deterministic while still proving the gateway’s timeout mapping. One later integration test checks the actual configured deadline.
