Use the real Week 1 Qwen server behind the gateway

The fake backend taught us whether the gateway contract is correct. This lesson checks a different claim: can that same contract successfully reach a real model server over HTTP and relay its result without exposing port 8001 to the client?

The two processes

Notebook client
/v1/chat/completions→ Gateway app
public contract + translation→ Week 1 server :8001
/generate, /generate/stream

Only the gateway knows that the backend happens to be on port 8001. The notebook client uses the gateway's public endpoint.

Practical 1: start the actual backend

Open a second terminal and leave this process running:

cd /Users/myatkaung/Desktop/production-llm-inference-lab
source .venv/bin/activate
uvicorn server:app --app-dir week-01-baseline-server --host 127.0.0.1 --port 8001

Then open and run 02-real-week1-http-backend.ipynb top to bottom. Its first code cell checks:

GET http://127.0.0.1:8001/health
→ {"status": "ok", ...}

If this fails, stop here. You are debugging the Week 1 server, not the gateway.

Worked example A: a real non-streaming request

The client sends the stable public request:

POST /v1/chat/completions
{"model":"local-qwen", "messages":[{"role":"user","content":"Explain caching in one sentence."}], "max_tokens":16}

The gateway's HttpWeek1Backend translates it to the Week 1 private request:

POST http://127.0.0.1:8001/generate
{"messages":[{"role":"user","content":"Explain caching in one sentence."}], "max_new_tokens":16}

The real Qwen response is parsed and mapped back to a public response. Your generated wording will vary, but the shape must include a gateway request ID, one assistant message, and token usage:

{
  "id": "req_...",
  "object": "chat.completion",
  "model": "local-qwen",
  "choices": [{"message": {"role": "assistant", "content": "..."}}],
  "usage": {"prompt_tokens": 36, "completion_tokens": 16, "total_tokens": 52}
}

Notice that the public response does not reveal Qwen/Qwen2.5-0.5B-Instruct, MPS, or port 8001.

Worked example B: actual streaming SSE

Set "stream": true. The gateway now calls /generate/stream, reads each backend SSE data: line, and emits a separate public SSE delta:

data: {"id":"req_...","choices":[{"delta":{"content":"Caching"}}]}

data: {"id":"req_...","choices":[{"delta":{"content":" is"}}]}

data: [DONE]

The notebook parses those events, asserts that there is text, and asserts that the final event is [DONE]. This is meaningful because the chunks came from the real model server—not a predetermined test list.

What this proves—and what it does not

Proves: the HTTP adapter can translate request fields, make a real model-server request, map a real result, and relay real streaming output through the stable gateway endpoint.

Does not yet prove: production load handling, cancellation propagation, overload protection, backend 5xx mapping, or metrics. Those are the next gateway exercises.

Retrieval check

If port 8001 changes to a vLLM server later, which code should change?

Replace or reconfigure the backend adapter. The public gateway route and client request should remain unchanged.

Why keep the fake-backend notebook after this real test exists?

It makes edge cases deterministic and fast. Use it for exact policy and error tests; use the real integration notebook to prove the adapter and server work together.
