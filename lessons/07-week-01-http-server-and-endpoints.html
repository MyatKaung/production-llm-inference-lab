The whole path

curl client→ FastAPI route→ chat template + tokenizer→ Qwen on MPS→ JSON or SSE

Worked example: non-streaming

The client sent this JSON to POST /generate:

{
  "messages": [{"role": "user", "content": "Explain caching in one sentence."}],
  "max_new_tokens": 16
}
  1. FastAPI validates the request. It accepts one non-empty message and a positive max_new_tokens. An empty messages list was rejected with HTTP 422 in our real test.
  2. get_engine() obtains one model engine. On the first request it constructs InferenceEngine, loading the tokenizer and Qwen model onto MPS. Later requests reuse it: model load is not repeated.
  3. make_inputs() formats the chat then tokenizes it. The model does not receive the raw English sentence. apply_chat_template(...) adds Qwen’s required chat markers, then produces token IDs and an attention mask. In our run, this request became 36 prompt tokens.
  4. model.generate() runs two phases. Prefill processes all 36 input tokens and builds the attention/KV state. Decode then predicts one new token at a time, using that cached state. Greedy decoding is used here because do_sample=False.
  5. The server removes the input tokens. generate() returns the prompt plus newly generated tokens. The slice output[0, prompt_tokens:] keeps only the completion; decoding those IDs makes readable text.
  6. FastAPI returns one JSON object. The live response produced 16 output tokens in about 1.69 seconds of measured generation time, roughly 9.49 effective output tokens/sec. The model-load time occurred before that timer, so it must be measured separately as cold-start time.

The same request, streamed

POST /generate/stream follows the same tokenization and model steps, but it changes how results leave the model:

  1. TokenQueueStreamer is passed to model.generate().
  2. The model invokes the streamer’s put() as it produces token IDs. The first call contains prompt IDs, so skip_prompt drops it.
  3. A background thread runs generation while the route reads token IDs from the queue.
  4. Each ID is decoded and yielded as one server-sent event (SSE), such as {"index": 0, "text": "C"}, then {"index": 1, "text": "aching"}.
  5. When generation ends, the server sends data: [DONE]. This tells the client that no more chunks are coming.

Why streaming feels faster: the final answer may take hundreds of milliseconds, but the UI can display the first decoded piece as soon as it arrives. That first-piece delay is time to first token (TTFT).

Three measurements you must not mix up

  • Cold start: process receives its first useful request until model/tokenizer are available. It includes model loading.
  • TTFT: request acceptance until the first SSE token chunk. It contains request overhead plus prefill, and usually some first decode work.
  • Total latency: request acceptance until the complete JSON response or [DONE]. It includes the entire decode loop.

Why the test suite matters

The seven passing tests use a fake engine. That proves the HTTP contract—validation, JSON shape, ordered SSE events, and completion signaling—without making every test download and run Qwen. The real curl calls add the missing integration evidence: the contract and the model work together.

Self-check

1. Why does the server slice generated IDs at prompt_tokens?

Because model.generate() returns the original prompt IDs followed by new IDs. The client should see only the new completion.

2. The first streamed pieces were “C” and “aching.” Why are they not necessarily words?

The model generates tokenizer units, not guaranteed whole words. The server decodes each emitted token ID, so chunks can split a word.

3. Why can’t 1.69 seconds be called cold-start time?

The server starts its timer inside InferenceEngine.generate(), after lazy model loading has already occurred. It measures model generation, not load time.
