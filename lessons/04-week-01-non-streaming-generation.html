Generate a complete answer, then measure it

Goal: run one deterministic generation and understand why the notebook slices prompt tokens out of the returned sequence.

Run this notebook cell

Return to practical-baseline.ipynb. If the kernel was restarted, rerun its first four code cells so generate_once() exists; then run:

smoke = generate_once('Explain caching in one sentence.')
print(smoke)

Worked example

model.generate() returns one sequence that contains both input and newly generated IDs:

[ prompt token 0, prompt token 1, ... prompt token 35,
  generated token 0, generated token 1, ... ]

This line removes the prompt:

new_tokens = output[0, inputs['input_ids'].shape[-1]:]

If the input was 36 tokens and the model generated 16 more, the slice starts at index 36. Decoding the entire sequence would expose the prompt/chat markers instead of just the assistant answer.

Practical experiment

# Keep generation deterministic. Change only the output cap.
short = generate_once('Explain caching in one sentence.', max_new_tokens=8)
long = generate_once('Explain caching in one sentence.', max_new_tokens=32)
print(short)
print(long)
  1. Record prompt_tokens for both runs.
  2. Compare output_tokens and total_latency_seconds.
  3. Did the answer stop naturally or hit your output cap?
Expected reasoning

The prompt token count should stay the same. A larger cap permits more decode steps, which can increase total latency. An answer may stop early at EOS or may be truncated by the cap.
